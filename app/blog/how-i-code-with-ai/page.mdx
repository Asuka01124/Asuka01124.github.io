# 我如何用 AI 写代码（而不被 AI 带偏）

<PostMeta date="2026-07-21T20:00:00" readingTime={6} />

<Cover src="/blog/how-i-code-with-ai-cover.avif" alt="我如何用 AI 写代码" caption="" />

最近我的信息流里出现了一堆让我头疼的词。

Harness。Loop Engineering。Context Architecture。Agent Orchestration Layer。Context-aware Multi-turn Task Decomposition Pipeline。

每个词都像一颗原子弹。配着 "This changes everything" 的推文，炸得我眼睛疼。

每隔两周，就有人跳出来告诉你：上一周的范式已经死了。现在的 Agent 开发必须这样、必须那样，少了一个中间层你就是原始人。架构图越来越密，箭头越来越多，一个简单的"让 AI 读代码然后改 bug"被拆成了七个节点、四个 Agent、三个评估层。热热闹闹，眼花缭乱。

然后你定睛一看——这不还是让 AI 改个 bug 吗？改了七个节点之后，结果比直接说"帮我修这个 bug"还好吗？不一定。

---

## 炒作机器的标准剧本

我慢慢摸清了这波 AI 炒作的标准流程：

**第一周**：某大厂/知名博主发一篇文章，标题通常是 "We built a new X for Agent"，配一张复杂的架构图。评论区一片 "This is the way"。

**第二周**：衍生概念井喷。Harness、Wrapper、Orchestrator、Middleware——每个团队都在给自己的那一层起一个更炫的名字。于是你在 GitHub 上看到一堆星星没超过 50 的"Agent Framework"，README 比代码还长。

**第三周**：有人问了一句："Wait，这东西比直接调 API 强在哪？" 评论区沉默。

**第四周**：新概念出现，循环往复。

我不是说这些工程完全没有价值。在真正的大规模场景下——几百个并发的 Agent 调用、复杂的权限管理、审计日志、多租户隔离——中间层确实有意义。但问题在于：**这些东西被当成"标配"在推销**，仿佛你不用这些中间层，你的 Agent 就不是"真正的 Agent"。

一个学生，一个独立开发者，甚至一个小团队，真的需要 Harness 吗？真的需要 Loop Engineering 吗？

大概率，不需要。

---

## Agent 真正需要的是什么？

让我们回到最基本的问题：Agent 到底是什么？

一个模型。收到你的指令。理解它。调用工具。返回结果。

就这些。没有魔法。没有"涌现的智能"。没有"自我意识"。就是一个**读指令 → 动手干 → 交结果**的循环。

这个循环的核心瓶颈从来不是"Agent 之间的通信协议是否优雅"，也不是"上下文压缩策略是否足够先进"。瓶颈只有一个：**你的指令有多清楚。**

你可以用最先进的 Multi-Agent 框架、最复杂的 Orchestration 层、最前沿的 Context Engineering——但如果你的初始指令是模糊的，产出的东西一定是歪的。

反过来，一个最朴素的单 Agent，配上一段写清楚了的自然语言计划，产出的质量往往超乎预期。

## 我的工作流：一个 MD 文件就够了

在我做 AsukaCode 和其他项目的过程中，我逐渐收敛到了一个极其简单的工作流。

**在项目根目录扔一个文件。** 叫 `PLAN.md`，叫 `TODO.md`，叫 `任务.txt`——随便。格式不重要。MD 可以，TXT 可以，Word 可以。就算你在 Notion 里写、在 Apple Notes 里写、在微信文件传输助手里写——都行。

重要的是里面的内容。大概是这样的结构：

```markdown
## 要做什么

把 XX 功能从 A 实现改成 B 实现。原因是 A 在处理
大文件时有性能问题（超过 100MB 会卡死）。

## 为什么要这样做

- A 用同步读取，大文件扛不住
- B 用流式读取，内存占用更小
- 当前用户反馈 XX 场景下经常崩溃

## 约束条件

- 不要改 C 模块的接口，其他功能依赖它
- 测试用例保持原样，新增的测试另外写
- 向后兼容旧版本的数据格式

## 验收标准

1. 100MB 文件处理在 3 秒内完成（现在是 15 秒）
2. 旧版本的数据文件能正常读取
3. 现有测试全部通过
```

就这些。没有流程图画布，没有 Agent 编排脚本，没有 Multi-turn 策略配置。

把这个文件扔给 Claude Code 或者任何一个靠谱的 Agent，它读一遍，理解上下文，动手干。干到一半卡住了？回去读你的计划。干完了？对照你的验收标准检查。

**这个过程的成功率，取决于你写得有多清楚——而不是你用了多少层中间件。**

---

## 写清楚为什么这么难？

"写清楚"听起来简单，实际操作起来是整件事里最难的部分。

因为大多数人（包括我）在写计划之前，**以为自己想清楚了，其实没有。**

你在脑子里有一个模糊的想法："这个模块好像性能不太好，改一下吧。" 然后你就把 Agent 叫过来："帮我优化这个模块的性能。" Agent 开始干活——改了几十处代码、换了数据结构、加了缓存层——然后你发现它改的根本不是你关心的那个瓶颈。因为你自己也不知道瓶颈在哪。

**写下来的过程，就是逼自己把模糊变成清晰的过程。**

当你被迫在 MD 文件里写 "当前是 15 秒，目标是 3 秒以内" 的时候，你就不得不先去测一下现在到底是多少秒。当你写 "约束条件：不要改 C 模块" 的时候，你就不得不先去了解一下 C 模块是干什么的、谁依赖它。当你写 "验收标准" 的时候，你就不得不定义什么叫"做完了"。

这些东西，没有一个 Agent 能替你搞清楚。**AI 不是魔法，它只是把你的意图翻译成代码。意图模糊，代码必然跑偏。**

---

## 一个反直觉的现象

有意思的事情来了。

一旦你把计划写得足够清楚——**你甚至不需要 Agent 了。**

因为很多时候，写清楚计划的过程本身就已经帮你理清了思路。你知道问题在哪、知道要改什么、知道怎么验证。剩下的编码工作，反而是最机械、最省心的一步。Agent 干也行，自己干也行。

真正值钱的东西，从来不是代码。是**那个计划文件。**

---

## 所以，别被带偏

如果你是一个在用 AI 写代码的人——不管是学生、独立开发者、还是工程师——我只有一句话想对你说：

**别怕那些你听不懂的词。**

Harness 是啥？不知道，也不用知道。Loop Engineering？听起来像过山车设计。Agent Orchestration Layer？大概是一个管弦乐队指挥？

你用不着这些。你需要的只是打开一个空白文件，写清楚：

1. 你要做什么
2. 为什么要做
3. 有什么限制
4. 怎么样算做完了

然后把它交给一个能读懂自然语言的模型。

如果 AI 跑偏了，先别急着换框架、加中间层、升级模型。先检查一下——**是不是你自己也没想清楚要什么？** 大概率，是的。

---

## 写在最后

AI 编程工具的进步是真实的，但围绕它的叙事机器也是真实的。每一个新概念都在试图让你相信——你缺的不是理解，而是工具。你缺的不是思考，而是框架。你缺的不是把事情想清楚，而是又一个中间层。

别信。

在这个行业里，**能把话说清楚的人，永远是稀缺的。** 而能把话说清楚的人加上一个最朴素的 Agent，就已经比那些画了七层架构图但说不清自己要做什么的团队强了。

写好你的计划。MD、Word、TXT——什么格式都行。

然后放手让 AI 干活。
