# AI 编码助手的难点，从来不只是调用模型

<PostMeta date="2026-08-23T20:00:00" readingTime={11} />

<Cover src="/blog/the-hard-part-of-ai-coding-assistants.png" alt="AsukaCode 终端 AI 编码助手界面" caption="AsukaCode 终端界面" />

如果只看最小实现，做一个 AI 编码助手似乎并不难。

准备一段 System Prompt，把用户输入发给模型，给模型几个读写文件和执行命令的工具，再把工具结果塞回上下文。模型继续判断、继续调用，直到它不再请求工具，一轮任务就结束了。

整个 Agent Loop 甚至可以写在几十行代码里。

我最初开始做 AsukaCode 时，也觉得最重要的部分应该是这个循环。只要模型足够聪明、工具定义足够清晰，它就能像一个真正的程序员一样在终端里工作。可当我试图把这个 Demo 变成一个自己愿意每天使用的工具时，事情迅速变得复杂起来。

模型调用反而成了最简单的一层。

真正困难的问题是：它应该看到什么？它可以做什么？执行到一半出错了怎么办？终端界面如何准确反映后端正在发生的事情？当对话塞满上下文窗口之后，它还记不记得最初的目标？

这些问题没有一个能靠“换个更强的模型”自动解决。

---

## 能调用工具，不等于会完成任务

最简单的 Agent Loop 大概是这样的：

```text
用户输入
  → 模型判断
  → 调用工具
  → 返回执行结果
  → 模型继续判断
  → 输出答案
```

这个闭环能跑起来，会带来一种很强的错觉：产品已经完成了八成，剩下的只是把界面做好看一点。

但“工具成功返回”与“任务被正确完成”之间，还有很长一段距离。

比如模型要修改一个函数。它需要先找到文件，理解调用关系，决定改动范围，然后精确编辑。修改之后，它还需要运行测试，读懂报错，判断错误来自自己的改动还是原有环境。如果测试命令长时间没有输出，程序要知道进程仍在运行，而不是把空白当成成功。如果 API 突然限流，它也不能直接丢掉已经完成的步骤，从头再来一遍。

每一步单独看都不神秘，但它们必须连成一条可靠的链。真正的编码任务也不会只走一次“模型 → 工具 → 模型”，而是会在读取、搜索、编辑、执行和纠错之间来回穿梭。

所以 Agent Loop 只是心脏。心脏会跳，并不意味着一个人就能走路。

---

## 第一个难点：给模型恰到好处的上下文

AI 编码助手最常见的问题，不是模型什么都不知道，而是它同时知道了太多无关的东西。

把整个仓库、所有历史消息和每次工具输出一股脑塞给模型，看起来最保险，实际上很快就会撞上上下文窗口。更麻烦的是，信息越多并不一定意味着判断越准。大量旧日志、重复代码和过期计划会稀释真正重要的目标。

可如果压缩得太激进，模型又会失忆。它可能忘记用户明确说过“不要改这个接口”，也可能忘记前面某个测试失败的真正原因，绕一圈后再次犯同样的错。

我在 AsukaCode 里做了四级上下文压缩：

1. 使用率到 50% 时，先做轻量的 Micro 压缩
2. 到 70% 时，裁剪较早且价值较低的工具结果
3. 到 75% 时，进一步限制各类消息的预算
4. 到 85% 时，再让模型生成结构化摘要

这套设计并不是什么漂亮的算法，它更像是在两种失败之间寻找平衡：一边是上下文溢出，另一边是任务失忆。

后来我越来越觉得，Context Engineering 这个词虽然被说得很玄，但核心问题其实很朴素：**在正确的时间，把正确的信息交给模型。**

不是越多越好，也不是越短越好。真正重要的是，目标、约束、当前状态和关键发现不能丢。

---

## 第二个难点：能力越强，越需要边界

一个只能回答问题的聊天机器人犯错，最多给你一段错误答案。一个能执行命令、删除文件和改写配置的 Agent 犯错，结果就完全不同了。

最省事的权限系统是每次都弹窗确认。但如果读一个文件要确认，搜索一次目录也要确认，用户很快就会形成肌肉记忆：不再阅读内容，只管一路按回车。看似严格的确认机制，最后只制造了更多噪音。

另一种极端是完全放行。体验确实流畅，但模型可能把一句模糊指令理解成超出预期的大范围修改。

AsukaCode 的做法是把操作分层：明显安全的读取可以直接执行；破坏性命令和越界写入需要确认；命中 denylist 的操作直接拒绝。Shell 命令也不能只靠字符串里有没有 `rm` 来判断，因为管道、重定向、子命令和不同参数都可能改变真实行为，所以权限层还需要解析命令结构、检查路径和识别操作对象。

这部分代码对模型能力没有任何提升。它不会让回答更聪明，也不会让 Benchmark 分数更高，但它决定了我敢不敢真的让工具动手。

这也是我开发过程中很重要的一次认知变化：**AI 工具的价值不只是“它能做多少”，还包括“它知道什么时候不能直接做”。**

---

## 第三个难点：让界面和真实状态保持一致

终端 UI 看起来只是一个输入框、一片消息区域和几个状态面板，但流式 Agent 的界面并不是普通聊天框。

同一时刻，模型可能正在输出思考内容，某个工具可能刚开始执行，权限弹窗正在等待用户决定，后台又更新了 Token 使用率。如果这些状态各走各的，很快就会出现奇怪的问题：工具明明结束了，界面还显示 Running；用户切换了会话，上一段流式输出却写进了新会话；权限弹窗还没处理，Agent 已经进入下一步。

为了让这些变化有一条统一路径，AsukaCode 使用 Pipeline 传递事件。后端会发出 `assistant_delta`、`tool_start`、`tool_end`、`permission`、`context_stats` 和 `finished` 等事件，TUI 再根据事件更新对应状态。

```text
Agent Loop
  → tool_start
  → permission
  → tool_end
  → assistant_delta
  → finished
```

这听上去像是常规的状态管理，但 Agent 有一个麻烦之处：它的流程不是预先写死的。下一步做什么由模型动态决定，界面只能观察事件，不能假设固定顺序。

因此，每个事件都必须带上足够的信息，每个会话也必须有明确的身份。否则一次迟到的异步回调，就可能污染整个对话状态。

用户不会关心这里用了 Pipeline、EventEmitter 还是别的模式。用户只会觉得这个工具“稳不稳”。而所谓的稳定，往往就藏在这些看不见的状态同步里。

---

## 第四个难点：失败不是例外，而是正常流程

写 Demo 时，我们习惯把成功路径放在最中间：API 正常返回、工具正常执行、网络保持连接、输出符合格式。

真实使用时，失败路径才是日常。

模型可能返回无法解析的工具参数，命令可能因为环境差异而失败，文件可能在读取后被其他进程修改，API 可能限流或过载，用户也可能在任务执行一半时拒绝权限。即使所有代码都没有 Bug，外部世界也不会一直配合。

这里最危险的处理方式是无脑重试。一个读取请求重试几次通常没问题，但一个具有副作用的命令如果已经成功执行，只是响应在返回途中丢失，再执行一次就可能产生完全不同的结果。

所以错误恢复不只是 `try/catch` 加一个循环。程序需要区分错误类型，判断操作是否可以安全重试，并把失败事实明确地交还给模型。模型也必须知道工具被拒绝了，而不是把“没有结果”误解成“可以换种方式绕过去”。

做 AI 编码助手之后，我才真正体会到：**失败处理不是成功逻辑旁边的补丁，它本身就是主流程的一部分。**

---

## 模型决定上限，工程决定下限

更强的模型当然重要。它能更准确地理解代码，更合理地规划步骤，也更容易从报错中找到原因。但在模型之外，还有大量工作决定着这个工具最终是什么样子。

上下文管理决定它会不会做着做着忘记目标；权限系统决定它能不能在真实项目里被信任；状态同步决定用户看到的是不是正在发生的事实；错误恢复决定一次网络波动会不会毁掉整轮任务。

这些模块不会出现在最吸引人的演示里。演示通常只展示一句指令之后，Agent 自动修改十几个文件并让测试全部通过。没人愿意展示 API 在第七步超时、终端尺寸突然变化、用户拒绝一个命令之后，系统如何把任务继续完成。

但后者才是我现在最关心的东西。

我以前会把 AI 编码助手理解成“模型套上工具”。现在我更愿意把它理解成一个在不确定环境里运行的交互式软件系统。模型只是其中最有能力、同时也最不可预测的组件。

---

## 为什么我还是选择自己做

既然这些问题如此麻烦，为什么不直接使用成熟工具？

我当然会用。自己做 AsukaCode，并不是因为我认为它已经能替代所有现有产品，而是因为只有真正实现一次，我才能看见那些被产品界面藏起来的取舍。

为什么有些工具每一步都要确认？为什么上下文用到某个比例后，回答突然变得不稳定？为什么恢复一段旧会话并不像读取聊天记录那么简单？为什么一个看似普通的终端输入框，也要处理多行文本、命令面板、模式切换和焦点状态？

这些问题，站在使用者的角度很容易归结为“体验不好”。站在开发者的角度，却必须继续往下追问：是哪一层丢失了信息？哪个状态没有被正确建模？哪种风险不应该交给模型自行判断？

AsukaCode 对我来说，首先是一个正在被我使用的工具，其次也是一间实验室。我可以在里面验证自己对 Agent、终端交互和软件工程的理解，然后亲自承担错误设计带来的后果。

这比再读十篇“如何用几十行代码实现 Agent”的教程有意思得多。

---

## 写在最后

调用模型真的不难。

难的是在模型忘记之前保留重要信息，在模型越界之前建立清晰边界，在异步事件交错时维护一致状态，在外部世界出错时仍然给用户一个可理解、可恢复的结果。

如果只追求一次漂亮的演示，几十行 Agent Loop 足够了。如果想做一个可以长期使用的工具，那几十行只是起点。

模型决定一个 AI 编码助手最聪明时能走多远，而模型之外的工程，决定它状态最差时会跌得多重。

后者可能不够性感，却是一个工具从“能跑”走向“能用”的真正距离。
