# 我让 AI 改了一个函数，然后开始追踪它留下的线索

<PostMeta date="2026-08-23T20:00:00" readingTime={10} />

<Cover src="/blog/the-hard-part-of-ai-coding-assistants.png" alt="AsukaCode 终端 AI 编码助手界面" caption="AsukaCode 终端界面" />

我第一次觉得 AI 编码助手像一个真正的工具，不是在它一次性写对代码的时候。

那次任务很普通：把一个配置解析函数改成支持环境变量覆盖，再补上测试。我把需求丢给 AsukaCode，它先搜索文件，打开类型定义，修改实现，运行测试。前几步顺得像演示视频，直到测试在第七步突然停住。

终端没有报错，也没有继续输出。状态栏却还亮着 `Running`。

我等了十几秒，按下中断。进程确实还活着，只是子进程把输出缓冲住了。重新执行后，测试通过；但模型根据第一次的空白结果，已经开始准备重写另一处逻辑。它没有变笨，系统只是把“还没结束”误报成了“没有结果”。

这件小事比一次漂亮的成功更值得记录。它让我重新检查自己正在做的东西：AI 编码助手最难的部分，从来不是把请求发给模型，而是让模型在一个真实、嘈杂、会出错的环境里工作。

## 一个循环，和一件能用的工具

最小的 Agent Loop 大概长这样：

```text
用户输入
  → 模型判断
  → 调用工具
  → 返回执行结果
  → 模型继续判断
  → 输出答案
```

这个循环能跑通，很容易制造一种错觉：产品已经完成了八成，剩下的只是把界面做得更漂亮。

可“工具成功返回”和“任务被正确完成”之间，隔着一整套工程。模型需要知道该看哪些文件，权限层需要知道哪些动作应该停下来问人，终端需要展示真实状态，错误恢复需要区分“命令失败”和“命令其实成功了但响应丢了”。

心脏会跳，并不代表身体已经学会走路。

## 1. 上下文不是仓库的复印件

AI 编码助手最常见的问题，不是模型什么都不知道，而是它同时知道了太多无关的东西。

把整个仓库、所有历史消息和每次工具输出全部塞进上下文，看起来最保险，实际上很快就会撞上窗口上限。更糟的是，旧日志、重复代码和已经失效的计划会把真正重要的约束冲淡。模型看见了更多字，却不一定看见了更关键的事实。

压缩得太用力也会失忆。它可能忘记“不要改这个接口”，忘记上一次测试失败的原因，甚至在绕了一圈后再次执行刚刚被拒绝的操作。

我在 AsukaCode 里做了四级压缩：

1. 使用率到 50% 时，先做轻量的 Micro 压缩；
2. 到 70% 时，裁剪较早且价值较低的工具结果；
3. 到 75% 时，进一步限制各类消息的预算；
4. 到 85% 时，让模型生成结构化摘要，再继续任务。

这不是什么神奇算法，更像是在两个坑之间走钢丝：一边是上下文溢出，另一边是任务失忆。

后来我把 Context Engineering 记成了一句很朴素的话：**在正确的时间，把正确的信息交给模型。**

目标、约束、当前状态和关键发现必须留下；十分钟前那段已经验证无效的日志，不需要占据最好的位置。

## 2. 工具越锋利，边界越要清楚

只能回答问题的聊天机器人犯错，最多给你一段错误答案。能执行命令、删除文件和改写配置的 Agent 犯错，结果就完全不同。

最省事的权限系统是每次都弹窗确认。但如果读一个文件、搜索一次目录都要确认，用户很快就会形成肌肉记忆：不再读内容，只管一路按回车。确认框变多了，判断反而变少了。

完全放行也不是答案。模型可能把“清理一下缓存”理解成删除范围过大的目录；一条带重定向的 Shell 命令，看起来没有 `rm`，实际却能覆盖重要文件。

AsukaCode 把操作分成几层：明显安全的读取可以直接执行；破坏性命令和越界写入需要确认；命中 denylist 的操作直接拒绝。Shell 权限不能只靠字符串搜索，还要解析管道、重定向、子命令、路径和参数。

```text
读取文件       → 直接执行
修改源码       → 展示变更，按策略确认
删除/覆盖文件  → 明确确认
越界路径       → 拒绝
```

这部分不会提高模型的 Benchmark 分数，却决定了我敢不敢让它触碰一个真实项目。AI 工具的价值不只是“它能做多少”，还包括“它知道什么时候不能直接做”。

## 3. 界面必须讲真话

终端 UI 看起来只是输入框、消息区域和几个状态面板，但流式 Agent 的界面不是普通聊天框。

同一时刻，模型可能正在输出内容，工具刚开始执行，权限弹窗等待用户决定，后台又更新了 Token 使用率。如果这些状态各走各的，就会出现一串让人不安的小谎言：工具明明结束了，界面还显示 `Running`；用户切换会话，上一段流式输出却写进了新会话；权限还没处理，Agent 已经进入下一步。

为了让变化走同一条路径，AsukaCode 使用 Pipeline 传递事件：

```text
Agent Loop
  → tool_start
  → permission
  → tool_end
  → assistant_delta
  → finished
```

关键不在事件名字，而在每个事件都带着会话身份和足够的上下文。Agent 的下一步由模型动态决定，界面不能假设固定顺序，只能忠实地呈现已经发生的事实。

用户不会关心这里用了 Pipeline 还是 EventEmitter。用户只会感觉这个工具稳不稳，而稳定往往就藏在一次迟到的回调有没有写错地方。

## 4. 失败不是异常分支，是主流程

真实使用时，失败才是日常：工具参数格式不对，命令在另一台机器上不存在，文件刚读取就被其他进程改了，API 突然限流，用户在任务中途拒绝权限。

最危险的处理方式是无脑重试。

读取请求重试几次通常没问题；具有副作用的命令如果已经成功执行，只是响应在返回途中丢失，再执行一次就可能重复发送邮件、重复迁移数据，或者把刚刚修好的文件覆盖掉。

所以错误恢复不能只是 `try/catch` 加一个循环。程序需要先判断错误类型，再判断操作是否幂等，最后把失败事实明确交还给模型。模型必须知道工具被拒绝了，而不是把“没有结果”误解成“可以换种方式绕过去”。

我越来越相信，失败处理不是成功逻辑旁边的补丁，它本身就是主流程的一部分。

## 一次任务的“尸检报告”

现在遇到异常，我会按下面的顺序回放，而不是先换一个更大的模型：

1. **目标还在吗？** 最近一次压缩有没有丢掉用户的原始约束？
2. **动作发生了吗？** 工具是没执行、执行失败，还是执行成功但回执丢失？
3. **界面说真话吗？** 当前显示的状态是否来自同一个会话和同一条事件链？
4. **重试安全吗？** 这一步是否有副作用，重复执行会发生什么？
5. **谁应该做决定？** 这是模型可以自行恢复的问题，还是必须交给用户确认的风险？

这五个问题很少出现在产品演示里，却比“模型又多会写一种框架”更能决定工具的日常体验。

## 模型决定上限，工程决定下限

更强的模型当然重要。它能更准确地理解代码，更合理地规划步骤，也更容易从报错中找出原因。但上下文管理决定它会不会做着做着忘记目标，权限系统决定它能不能被信任，状态同步决定用户看到的是不是正在发生的事实，错误恢复决定一次网络波动会不会毁掉整轮任务。

演示喜欢展示“一句话修改十几个文件并让测试全部通过”。我现在更想看另一段录像：API 在第七步超时，用户拒绝一个命令，终端尺寸突然变化，系统仍然把任务停在一个可理解、可恢复的位置。

那才是软件真正面对的世界。

## 为什么我还在自己做

我当然会使用成熟工具。自己做 AsukaCode，不是因为我认为它已经能替代所有产品，而是因为只有真正实现一次，才能看见那些被界面藏起来的取舍。

为什么有些工具每一步都确认？为什么上下文用到某个比例后，回答突然不稳定？为什么恢复旧会话不像读取聊天记录那么简单？为什么一个终端输入框也要处理多行文本、命令面板、模式切换和焦点状态？

AsukaCode 对我来说，首先是一个正在被我使用的工具，其次是一间实验室。我在里面验证自己对 Agent、终端交互和软件工程的理解，也亲自承担错误设计的后果。

调用 API 只用了很短的时间，剩下的时间都在处理真实世界。这个比例有点反直觉，却正是它有意思的地方。

## 写在最后

一个 Agent Loop 可以用几十行代码写出来。一个值得每天使用的 AI 编码助手，需要另外几千个决定：哪些信息留下，哪些动作暂停，哪些状态展示，哪些错误重试，哪些风险必须让人看见。

模型最聪明时能走多远，决定了工具的上限；模型状态最差时会跌得多重，决定了用户还会不会继续使用它。

后者不够性感，却是“能跑”走向“能用”的真正距离。
