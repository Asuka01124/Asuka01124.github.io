# 当 Agent 开始执行命令，终端就不再只是终端

<PostMeta date="2026-09-08T20:00:00" readingTime={8} />

我以前把终端 UI 想得很简单：一个输入框，一块输出区域，再加上几行状态文字。

只要 Agent 能调用工具，界面甚至可以先放一放。模型负责思考，工具负责执行，终端负责把结果显示出来——这听起来像一条清晰的分工。

直到我开始真正使用 AsukaCode，才发现这条分工根本不存在。

当 Agent 能够搜索文件、修改代码、执行测试，终端就不再是一个被动的输出窗口。它同时承担了上下文的边界、权限的闸门、任务的进度条，以及用户最后的判断权。界面里的一个小状态如果说错了，模型可能会走错下一步；一个没有被展示的等待，可能会让用户误以为程序已经卡死；一次无法打断的命令，则会把“辅助”变成“接管”。

## 一个输入框，背后藏着四种状态

普通聊天的输入框通常只有两种状态：可以输入，或者正在发送。

Agent 的输入框复杂得多。用户可能正在输入一条新消息，模型可能正在流式输出，工具可能正在运行，权限对话框可能等待决定，而当前会话还可能已经被切换了。

这些状态不是互相独立的。它们像一组交通信号灯，任何一个灯显示错误，都会影响用户对整个系统的判断。

我后来把一次交互拆成了几条更具体的路径：

```text
用户输入
  → 会话接收
  → Agent 思考
  → 工具执行
  → 权限确认（可能发生）
  → 结果回传
  → Agent 继续或结束
```

这里的“可能发生”很重要。权限弹窗不是一个固定步骤，工具也不一定只执行一次。Agent 的路径由当前上下文和模型决定，界面不能假设下一秒一定会发生什么，只能准确表达现在发生了什么。

这也是我不太喜欢把 Agent UI 做成普通聊天气泡的原因。聊天气泡擅长表达“谁说了什么”，但不擅长表达“谁正在做什么、为什么停下来、下一步需要谁做决定”。

## 状态比动画更重要

终端产品很容易陷入一个误区：只要有流式文字、旋转图标和闪烁光标，体验就会显得很有生命力。

但用户真正需要的不是动画，而是确定性。

他想知道的其实是几个朴素的问题：

- 现在是模型在思考，还是某个命令正在执行？
- 这个命令有没有修改文件？
- 程序是在等待我的确认，还是网络暂时没有响应？
- 我按下中断后，任务真的停了吗？
- 当前显示的内容属于哪个会话？

这些问题不能靠更快的动画回答，只能靠清晰的状态模型回答。

在 AsukaCode 里，我让 Agent 和 UI 通过事件传递状态。工具开始时发出 `tool_start`，结束时发出 `tool_end`；需要用户决定时发出 `permission`；任务完成时发出 `finished`。事件本身不是 UI 细节，而是系统对外承诺的一部分。

```text
tool_start
  → 正在执行：npm test
  → tool_end
  → 测试结果返回给 Agent
```

如果中间出了错误，也要有明确的终点。一个命令不能永远停在 `Running`，一个已经被拒绝的操作不能被伪装成“暂时没有结果”。用户可以接受失败，却很难接受系统不知道自己是否失败。

## 可打断，意味着系统真的承认人还在场

很多 Agent 演示都强调自动化：输入一句话，然后等待它连续完成十几个步骤。

但真实工作不是无人值守的流水线。用户会突然想起一个约束，会发现模型理解错了目标，会看到一条不该执行的命令，也可能只是想先看看当前状态。

所以“停止”不是一个锦上添花的快捷键，而是 Agent 的基本能力。

实现可打断比我想象中麻烦。停止输入不等于停止模型请求，停止模型请求也不等于停止子进程；子进程结束了，还要确保事件流不会把迟到的输出写回界面。若当前任务已经切换到另一个会话，旧任务的回调更不能污染新的消息列表。

我现在会把中断看成一次完整的状态迁移：

```text
运行中
  → 收到中断
  → 停止等待中的请求或子进程
  → 忽略迟到事件
  → 写入可解释的结束原因
  → 回到可继续输入的状态
```

最后一步尤其重要。一个好的中断不会把用户留在半死不活的界面里，而是让他知道任务停在哪里、已经做了什么、接下来还能怎么继续。

## 权限弹窗不是打断，而是协商

当 Agent 只能读取文件时，权限问题不明显。它一旦可以执行 Shell 命令，权限就从后台实现变成了用户体验。

最简单的方案是每次都询问。但如果读取目录、查看文件、运行无副作用的测试也要弹窗，用户会快速失去耐心；更危险的方案是全部放行，因为“执行测试”和“删除目录”可能都只是一个工具调用。

我更愿意把权限确认理解为协商，而不是阻塞：系统先判断风险，用户再对高风险动作做决定。

```text
低风险读取       → 直接执行
普通构建/测试     → 根据规则执行
修改或覆盖文件   → 展示动作并确认
明显越界操作     → 直接拒绝
```

这要求权限层理解命令的结构，而不只是寻找几个危险字符串。一条命令可能通过管道、重定向、子命令或变量展开产生副作用。用户看到的确认内容也应该足够具体：到底要执行什么，作用范围在哪里，拒绝之后任务会怎样。

如果弹窗只写着“允许工具执行吗？”，用户并没有获得真正的判断信息。确认框的价值不在于让用户按一个按钮，而在于把原本隐藏的风险翻译成人能理解的事实。

## 终端的优势不是复古，而是可见性

有人觉得终端不够友好，因为它没有卡片、插图和复杂的引导。我的感受正好相反：终端把工具做了什么暴露得更直接。

文件路径是文字，命令是文字，错误输出是文字，等待状态也是文字。它不太会替你把危险的操作包装成一个看起来无害的按钮。

当然，这种可见性也会带来负担。一次长任务可能产生大量日志，模型的思考、工具参数和测试输出会争夺同一块屏幕。如果所有内容都平铺出来，信息透明反而会变成噪音。

因此终端 UI 也需要设计层次：用户消息应该容易找到，工具调用要能快速识别，详细输出可以折叠，错误和权限请求必须醒目，当前任务的整体状态则要始终可见。

我喜欢把它想成驾驶舱，而不是日志窗口。驾驶舱不会把发动机里的每个螺丝都展示给驾驶员，但它会把速度、航向、警告和失控风险放在正确的位置。

## 模式切换：让用户知道自己拥有哪种能力

AsukaCode 里有 Build 和 Plan 两种模式。Plan 模式只能观察和规划，Build 模式才允许修改文件和执行更有副作用的操作。

这件事表面上是工具过滤，实际上也是认知保护。

当用户只想让 Agent 分析一个问题时，他不应该还要担心模型会不会顺手改掉代码；当用户明确进入构建阶段时，界面也应该清楚表达权限范围已经变化。

模式切换不能只存在于内部变量里。它需要出现在状态栏、提示词和权限检查的同一条链路中：

```text
用户切换模式
  → 会话状态更新
  → UI 显示新模式
  → Agent 获得对应提示词
  → 工具列表和权限规则同步变化
```

如果这四件事不同步，就会出现很难排查的问题：界面显示 Plan，模型却仍然能调用编辑工具；或者工具已经被限制，用户却不知道为什么刚才可以做的事现在失败了。

好的交互不是把所有内部细节都告诉用户，而是在用户需要做决定的地方，不隐藏决定所依赖的事实。

## 我开始重新理解“人机协作”

以前说人机协作，我脑中更像是一条流水线：人提出目标，机器负责执行，人最后验收。

但一个真正可用的 Agent 更像是两个人一起工作。人负责目标、取舍和边界，模型负责搜索、组合和重复劳动。两者之间需要不断交换上下文，也需要在不确定的时候停下来确认。

这解释了为什么一个很小的终端功能，最后会牵动那么多代码。输入框决定消息怎样进入系统，事件管道决定状态怎样传播，权限层决定风险怎样暴露，任务面板决定进度怎样被理解，取消逻辑决定用户能不能重新拿回控制权。

它们都不是“界面外观”的问题，而是协作协议的一部分。

## 写在最后

我仍然喜欢终端的克制感，但现在不再把它当成一个黑色的外壳。

当 Agent 只能回答问题时，终端可以只是聊天窗口；当 Agent 开始读取文件、执行命令、修改项目，终端就变成了人与自动化系统之间的控制面板。

它需要告诉用户事实，承认等待，允许中断，暴露风险，并且在出错之后留下继续工作的路。

模型决定 Agent 能理解什么，工具决定 Agent 能做什么，而交互决定人敢不敢把一部分工作交给它。

这也是我继续打磨 AsukaCode 的原因：我想做的不是一个会调用工具的聊天机器人，而是一个在每次行动之前、之中和之后，都愿意把控制权交还给人的工具。
