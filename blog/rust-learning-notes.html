Rust 学习笔记：从所有权到生命周期

2026-08-14 20:00·阅读时间：7 分钟

为什么是 Rust

接触过的语言大多处在两个极端：要么靠垃圾回收器兜底，写得轻松，却在性能和确定性上处处受限；要么要求手动管理内存，快是快了，但空指针、悬垂指针、数据竞争这些坑一个不少。

Rust 声称能把两者结合起来——内存安全，却不需要垃圾回收器。这听起来好得不真实，我决定亲自上手验证一下。

所有权：把「谁负责释放」变成编译期问题

Rust 的所有权系统只有三条规则，却推翻了我此前建立的几乎所有直觉：

  1. 每个值都有一个唯一的「所有者」；
  2. 同一时刻，一个值只能有一个所有者；
  3. 所有者离开作用域时，这个值会被自动释放。

第三条规则意味着 Rust 不需要 GC 就能自动回收内存——释放时机在编译期就已经由作用域确定。真正让我不适应的是第二条：赋值并不会复制数据，而是转移所有权。

fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // 所有权从 s1 转移到 s2

    // println!("{}", s1); // 编译错误：s1 已经失效
    println!("{}", s2);
}

String 的数据存放在堆上，所谓「转移」其实只是把栈上的指针、长度、容量整体搬过去，代价极低；同时 s1 被立即标记为失效，杜绝了同一块内存被释放两次的可能。

这个设计的动机，我是后来才慢慢想明白的：Rust 想让你在编译期就回答「这块内存到底由谁负责释放」。它不接受等到运行时才发现 double free 或 use-after-free，所以干脆在赋值的那一刻就掐断了所有悬垂引用的来源。

借用与引用：共享而不转移所有权

如果每次传参都要转移所有权，那函数用完还得把值再传回来，代码会又臭又长。Rust 提供了「借用」：在不转移所有权的前提下，让别人临时用一下你的值。

fn calculate_length(s: &String) -> usize {
    s.len()
}

fn main() {
    let s1 = String::from("hello");
    let len = calculate_length(&s1); // 借用 s1，所有权仍在 s1 手中

    println!("{} 的长度是 {}", s1, len); // s1 依然有效
}

只读共享很安全，但有时函数确实需要修改数据，这时就需要可变引用：

fn push_world(s: &mut String) {
    s.push_str(", world!");
}

fn main() {
    let mut s = String::from("hello");
    push_world(&mut s);
    println!("{}", s); // "hello, world!"
}

可变引用有一条著名的规则：同一时刻，对同一数据只能存在一个可变引用。

let mut s = String::from("hello");
let r1 = &mut s;
let r2 = &mut s; // 编译错误：不能同时持有两个可变引用

这条规则初看很烦，但它的目的直截了当——在编译期就杜绝数据竞争。一旦你接受了「要么多个只读、要么一个可写」这个模型，很多并发 bug 的温床就被连根拔掉了。

生命周期：给引用标注「有效期」

所有权和借用能回答「谁拥有、谁能用」，却还缺一块拼图：一个引用到底能活多久？

看这个函数：

// 编译错误：缺少生命周期标注
fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() { x } else { y }
}

它的返回值要么借用自 x，要么借用自 y。编译器看到一个「借来的」返回值，却无法确定它到底借自谁，也就无法保证调用方不会持有它超出原数据的寿命。它需要你明确声明三者之间的存活关系：

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

'a 不是什么新概念，它只是一个占位符，用来表达「这三个引用共享同一个有效期」。更准确地说，它承诺：返回的引用活得和 x、y 中较短的那个一样久。Rust 会在编译期检查每一个调用点，确保没有任何地方让这个返回值比它的来源活得更久：

fn main() {
    let string1 = String::from("长字符串");
    let result;
    {
        let string2 = String::from("短");
        result = longest(&string1, &string2);
    } // string2 在这里被释放

    // println!("{}", result); // 编译错误：result 的有效期被绑定到了 string2
}

这里有两个关键认知，是我绕了不少弯路才建立起来的：

  1. 生命周期标注不改变任何东西的存活时间。它只是声明关系、交给编译器检查，并不会在运行时「延长」引用的寿命。很多初学者（包括我）一开始都误以为 'a 是在控制内存的生死，其实不是。
  2. 大多数时候你根本不用写 'a。Rust 有生命周期省略规则，函数体内一眼能看穿的场景它会自动推断，只有跨函数、返回借用值这类「编译器猜不到」的情况才需要手动标注。

所有权如何延伸到并发

生命周期回答的是「引用能活多久」，而所有权系统还有一层更深的推论：如果一个值能被安全地转移到另一个线程，数据竞争就可以在编译期被消灭。

use std::thread;

fn main() {
    let v = vec![1, 2, 3];

    let handle = thread::spawn(move || {
        println!("子线程拿到: {:?}", v);
    });

    handle.join().unwrap();
}

move 把 v 的所有权整体搬进新线程，主线程从此不能再碰它。这从编译期就杜绝了「两个线程同时读写同一块内存」的可能——这就是 Rust 引以为傲的「无畏并发」，它靠的不是程序员的谨慎，而是所有权规则本身。

学习心得

  1. 最难的不是语法，是心智模型的切换。 我卡得最久的不是 & 和 &mut 的写法，而是接受「赋值会转移所有权」这件事。习惯了「赋值就是复制」之后，突然发现 let s2 = s1 之后 s1 就没了，这种不协调感持续了相当一段时间。但跨过这道坎后，很多以前只能靠经验回避的 bug 就自然消失了。

  2. 生命周期标注是写给编译器的契约，不是写给运行时的。 我一度以为 'a 在控制引用存活的时长，后来才明白它什么都不做，只是告诉编译器「这几个引用有关系，你帮我检查一下」。想通这一点，那些看似神秘的标注就变得机械而简单了。

  3. 编译器确实是队友。 Rust 的报错往往不止说「这里错了」，还会解释为什么错、建议怎么改。相比其他语言的一行堆栈，这种「结对编程」式的反馈让我少走了很多弯路。一开始觉得它在处处刁难，后来才意识到，它是在帮我补上心智模型里缺失的那一块。

总结

Rust 的学习曲线确实陡峭，但它提供的内存安全、零成本抽象与并发安全，让它成为系统编程、WebAssembly、嵌入式等领域的强力选项。

而对我而言，这段学习最大的收获不是学会了某门语言，而是重新理解了「内存」这件事——所有权、借用、生命周期，本质上是在用一套编译期的规则，把原本要靠经验和运气去规避的 bug，变成了编译器替你兜底。这份确定性，是我在其他语言里没有体验过的。
